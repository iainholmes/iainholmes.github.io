# Private preparation and release handoff

The only public artwork inventory is `data/artwork-locks.json`: append-only pins for already published/withdrawn editions. The existing photo registry owns permanent chronological `plate_no` values, shown as actual captions such as `TRA Plate No. 006`; the next number is assigned only at actual publication, never during private reservation. An unused reserve is private, not a public registry with a hidden UI. Never push private packets, drafts, unused JPEGs, generated prompts, originals or identity references to any public branch. GitHub branches and raw file URLs are public even when Pages omits them.

## Shared storage

Use the connected Google Drive folder **Rupert Atlas Private Staging**, containing exactly one operational raw JSON file named **atlas-preparation.json**. This owner-only folder/file was initialized and authenticated upload/download was verified. The initialized packet is deliberately empty and is **not ready**. A separate `atlas-private-persistence-probe.json` is integration-test data and must never be selected as preparation.

Discover the folder once by exact name and retain its verified ID in private task context. Search/list inside that verified folder for the operational file; refuse ambiguous duplicates. Before every fetch/update, read folder and file metadata: require `shared:false`, exactly one `user/owner` permission, and the correct parent. Stop if metadata is unavailable or any additional/public/domain permission exists. Do not change sharing. Both scheduled executions must use the authorized Drive account/connection that can read this same file.

Fetch stored raw JSON with authenticated `download_raw_file:true, include_base64:false`. Materialize the returned authenticated file reference immediately into `rupert/_private/...` with mode 0600; never expose or persist its expiring bearer URL. A Drive file ID is persistent; a workspace path or signed download URL is not. Never print packet content/base64, attach its images, describe unused artwork, or put candidates in a readiness report.

There is one scheduled writer: Monday/Wednesday preparation. It replaces the same operational file **only after sealing and validation**, using Drive `update_file` with a local file reference, not `upload_file` which would create a duplicate. Read the prior modification time before preparation and recheck immediately before update; stop if another preparation writer changed it. The publisher is a read-only consumer. No database or extra automation is required. Drive does not provide a compare-and-swap through this connector, so simultaneous preparation writers are unsupported: do not run overlapping preparations. Keep the old validated packet if the new attempt fails. After an update, fetch/read back and compare exact bytes/checksum and permissions before claiming it was persisted.

Master, its edition/release log and immutable pins are the authority for consumed artwork. A private “available” flag can never override published usage. On the next preparation, discard reserve entries already present in master; do not copy, replace or regenerate their public bytes. A publisher retry checks the actual master slot first and exits idempotently if already released and verified.

## Packet contract

`private-staging.mjs seal PRIVATE_INPUT.json PRIVATE_PACKET.json` validates and writes an ignored, mode-0600 packet. Outputs must resolve inside the canonical ignored `_private` directory; symlink escapes are rejected. All commands use the real clock. Checksums detect corruption, not independent proof of truthful research: only the authorized editor may approve genuine evidence.

Input fields:

- `type:"rupert-private-preparation"`, `version:1`, actual `prepared_at`, target `edition_id`, `slot`, Saturday/Sunday `weekend`.
- Exactly two ordered `candidates`: `key` is `primary`/`alternative`; `independence_key` identifies the actual shared closure/access area. Two routes in one preserve are not independent. Each contains a complete canonical **draft** `edition`, optional additive public `places`, dated official `checks`, and `verification`.
- `verification`: actual `reviewed_at`; true `official_access`, `dog_rules`, `parking`, `route`, `coordinates`, `current_conditions`; a substantive `note` supported by genuinely read official sources. Public coordinates must be verified. Candidate evidence is at most 48 hours old at consumption. Schema checks and the existing approved-host/access/reuse rules apply. Existing public place records cannot be overwritten. Preparation review is not tomorrow's release approval.
- `artworks`: one to four approved, genuinely unused original illustrations. Each contains a canonical editorial `plate` photo `record`, independent `artwork` metadata (`image_id`, private `brief`, `characters`), `composition_key`, `review`, responsive `files`, and `visual`.
- Use opaque IDs `atlas-plate-` plus 12 random lowercase hex digits. `record.file` equals its ID; private ownership is `reserve/ID`, `style_version` remains `atlas-engraved-3`, `created_at` is the actual generation date. No destination is part of ownership, selection or generation. A candidate's private `photo` may use an unassigned placeholder with meaningful alt text; staging replaces it from the chosen reserve record.
- `files` maps precisely `FILE-WIDTH.jpg` to `{base64,sha256}`. Import through the existing pixels-only `prep_photos.py` **inside a private assembly**, not the public checkout. Each JPEG must fit the existing size budget, match its registry dimensions, have stripped metadata and a 4:5 boundary. `artwork-fingerprint.py` produces `visual` from the smallest JPEG using Pillow.
- `review`: actual `reviewed_at`; true `likeness`, `style`, `composition`, `originality`; substantive `note`. These are editorial attestations requiring real visual inspection, not automatically inferred from pixels. Compare supplied private dog photos for identity and the latest six published prints for style and variety. Do not emit unused illustrations or briefs to the user while reviewing them. If generation/inspection cannot remain private, stop and report that capability gap.

The packet gets a checksum when sealed. Exact normalized pixel identity and a conservative perceptual-hash similarity gate catch duplicates/re-encodings; they do not prove artistic originality. Structural composition keys cannot repeat within the unused reserve or the latest three keyed publications. Older accepted plates are reviewed visually, not given invented structural histories. The approved palette, vintage print treatment, dog identities/collars and 4:5 format remain fixed.

## Publisher procedure

1. Fetch current master and follow `PUBLISHING.md`. If the actual slot is already released, validate its pinned bytes and live state and stop. If an early wake-up precedes 07:00, wait/recheck the real clock at the due instant; do not claim the slot ran early.
2. Fetch the verified private packet from Drive. Run `private-staging.mjs check PRIVATE_PACKET`. If missing, stale, incomplete or inaccessible, report that concrete blocker. Do not commit any partial preparation or silently claim publication.
3. Run `private-staging.mjs stage PRIVATE_PACKET PRIVATE_WORK`. Default selection applies existing access/reuse rules and binds one deterministic unused reserve item to the candidate. `--alternative` assembles the independently verified backup. All draft JSON, registry entries, JPEGs and generated output stay inside `PRIVATE_WORK/rupert`, under the ignored `_private` directory. This is a fresh copy of current production plus additive candidate data; existing private opt-in history is copied only into the ignored assembly input.
4. Within the assembly, genuinely reverify publication-day official access, dog rules, route/parking, current conditions and public coordinates; append truthful evidence. Run its canonical `publish.mjs refresh EDITION_ID`, read actual NWS forecast/alerts and update advice. Perform a fresh substantive editorial review against that exact refreshed issue and selected artwork. Prepared approval, a different destination's weather or an old review cannot unlock publication.
5. Run the existing source/regression tests and focused publication/privacy checks in the isolated assembly. Then `private-staging.mjs publish PRIVATE_WORK` runs the unmodified eligibility gates as a dry-run. If the primary fails, report the private reason internally and assemble/reverify the alternative; the same unused illustration can remain selected. Never carry approval/forecast between alternatives. If both fail, report the specific blocker without spoilers.
6. `private-staging.mjs publish PRIVATE_WORK --apply` uses the real canonical release command, pins the new association only after the guards pass, builds and privacy-audits the released assembly. Failures leave the public checkout untouched and retain private logs. It rechecks the public data baseline before copying only audited public differences. New files in the public checkout are now a validated actual release, not a draft. Filesystem integration is not a remote transaction: if interrupted, rebuild/check/audit before any commit; never upload partial output.
7. Before committing, run public build/check, `audit --history`, inspect a `/rupert/`-only diff and re-fetch master. Respect the lease and reconcile concurrent work; publish one coherent final commit without force. No draft/unused asset may occur in the commit or its history. Verify master, successful Pages deployment and live byte parity. The private reserve needs no “consumed” write during publishing, avoiding two cloud writers. Historical pins/bytes/registry/association can never be changed on retry.

That external change requires the user's scheduling decision; a repository patch cannot change executor capabilities.
